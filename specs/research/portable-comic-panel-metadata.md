# ACBF carries panels across compatible readers

Continuation note, 2026-10-07: the source/parser research below predates the
[actual Android UI tests](android-reader-validation.md) and
[completed synthesis](end-to-end-validation.md). Its statements that no UI or

Research checked **2026-10-07**. This report informs the [vision](../vision/comic-panel-cli.md); it does not settle the implementation plan.

**A CBZ containing ACBF 1.1 metadata is the strongest verified candidate for portable, precomputed panel navigation.** Three open-source readers have inspected source paths that discover embedded ACBF, parse ordered panel regions, and navigate those regions: ACBF Viewer, ACBF Viewer for Android, and KDE Peruse. The strongest platform evidence is Linux and Android; Windows distribution needs qualification, and no native macOS or iOS/iPadOS candidate meeting the complete requirement was verified. An existing browser reader consumes ACBF but requires an unpacked, hosted comic rather than opening the CBZ directly. A synthetic archive passed the official schema, and its extracted metadata was successfully consumed by the Android reader's actual parser; no reader GUI was tested. ACBF is therefore a grounded recommendation, **not a guarantee of panel reading in every CBZ reader or on every platform**. ([ACBF specification](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Specifications), [Android parser](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer-for-Android/blob/1be5e700e793dd864828bbc48927bf28d2f43970/acbf/acbfdocument.py), [browser reader](https://github.com/ragtag/panel-by-panel))

The proposed CLI needs the third: its work only reaches the reader if the reader consumes the generated regions and their sequence. ## ACBF expresses the regions that ordinary catalog metadata lacks

ComicInfo.xml's established page fields describe image identity, dimensions, page type, bookmarks, and spreads; they do not encode panel polygons or within-page sequence. CoMet's published fields likewise do not provide panel geometry. ComicInfo can complement ACBF for library organization, but adding private panel XML would create a new reader integration requirement. EPUB Region-Based Navigation does standardize ordered regions, including nested regions, but changes the output container; W3C also cautions that few reading systems support it. ([ComicInfo schema](https://github.com/anansi-project/comicinfo/blob/main/schema/v2.0/ComicInfo.xsd), [CoMet specification](https://www.denvog.com/wordpress/comet/comet-specification/), [EPUB region navigation](https://idpf.org/epub/renditions/region-nav/), [W3C support warning](https://w3c.github.io/epub-specs/epub33/fxl-a11y-tech/#region-based-navigation))

**ACBF 1.1 frames are ordered polygons in image-pixel coordinates.** Each page references an image and contains zero or more `frame` elements. Their XML order is their reading order; overlapping frames are permitted. A page without frames has no frame-level zoom under the specification. This preserves a whole-page representation while allowing selected views into it. It does not guarantee a polygon-shaped crop: inspected Android and Peruse focus code fits each polygon's rectangular bounds. ([Frame specification](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Body-Section-Definition#frame), [Android focus](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer-for-Android/blob/1be5e700e793dd864828bbc48927bf28d2f43970/main.py#L785-L815), [Peruse focus](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/app/qml/viewers/ImageBrowser.qml#L278-L307))

The recommended conservative archive profile is a normal CBZ/ZIP containing full-page images with sortable names and exactly one lowercase, root-level `metadata.acbf`. The basename is a convention, not a standard requirement. Root placement matters because both ACBF Viewers inspect only the extraction root; Peruse can discover nested metadata. Relative image paths then resolve predictably. Alphabetically ordered image filenames also support ordinary archive readers that ignore ACBF, although their exact fallback behavior still needs testing. ([Embedding specification](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Specifications#embedding-acbf-files-and-compatibility-with-popular-comic-book-formats), [desktop discovery](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer/blob/a77484ab45cba6da29efa974b180cdf95a79b48e/src/fileprepare.py#L100-L106), [Android discovery](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer-for-Android/blob/1be5e700e793dd864828bbc48927bf28d2f43970/acbf/fileprepare.py#L191-L198), [Peruse discovery](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/qtquick/ArchiveBookModel.cpp#L243-L281))

For example, the synthetic probe archive contains only `0000.png`, `0001.png`, and `metadata.acbf`. Both images are 200 × 300 pixels. The following complete metadata document passed the official 1.1 XSD; it is an illustrative fixture, not a settled output template:

```xml
<?xml version="1.0" encoding="utf-8"?>
<ACBF xmlns="http://www.acbf.info/xml/acbf/1.1">
  <meta-data>
    <book-info>
      <author><nickname>Synthetic research fixture</nickname></author>
      <book-title>Panel compatibility probe</book-title>
      <coverpage>
        <image href="0000.png"/>
        <frame points="0,0 199,0 199,299 0,299"/>
      </coverpage>
    </book-info>
    <publish-info><publisher>Synthetic fixture</publisher></publish-info>
    <document-info>
      <creation-date value="2026-10-07">2026-10-07</creation-date>
      <id>synthetic-panel-probe</id>
    </document-info>
  </meta-data>
  <body>
    <page>
      <image href="0001.png"/>
      <frame points="110,10 190,10 190,140 110,140"/>
      <frame points="10,160 190,160 190,290 10,290"/>
    </page>
  </body>
</ACBF>
```

The cover appears once, followed by a page whose upper-right region precedes its lower region. **Cover is structural** in ACBF: readers prepend it to body pages, and it can itself contain frames. Repeating the first image as both cover and body duplicates that page. A story page used as the required cover need not lose its panels. A cover-only framed book needs special verification because the inspected Viewers' `has_frames` detection scans body pages. ([Cover definition](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Meta-data-Section-Definition#coverpage), [desktop page/frame mapping](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer/blob/a77484ab45cba6da29efa974b180cdf95a79b48e/src/acbfdocument.py#L253-L316))

Emit integer coordinates with **one ASCII space between point pairs**: the inspected Python readers parse integers and split on literal spaces. Coordinates must describe the final stored image after orientation and scaling, not the prototype's 0–1000 coordinate space. Also avoid mixing proposed 1.2 fields into a 1.1 document: `reading-direction` is a proposed extension absent from the released 1.1 schema. Explicit frame order still determines story sequence; navigation direction is a separate reader concern. ([Android parser](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer-for-Android/blob/1be5e700e793dd864828bbc48927bf28d2f43970/acbf/acbfdocument.py#L286-L302), [reading-direction proposal](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Meta-data-Section-Definition#reading-direction-new-in-12), [pinned 1.1 schema](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/blob/e033e004e2897fe20ad09cbd649a8ba1d6b38d09/XML%20Schema/acbf-1.1.xsd))

## The probe proves parser interoperability, with clear limits

A scratch-only experiment created a DEFLATE CBZ containing synthetic images and the metadata above, extracted it with Python ZIP handling, validated the XML with the authoritative XSD, and loaded it through the upstream Android `ACBFDocument` class. An unrelated constants module supplied font/platform defaults; no parser methods were replaced. The observed result was valid metadata, `has_frames=true`, the correct cover/body image references, one cover polygon, and two body polygons in XML order. This is stronger evidence than a feature checklist, while remaining **a metadata-parser test, not an installed-Android-app test**. ([Upstream class](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Viewer-for-Android/blob/1be5e700e793dd864828bbc48927bf28d2f43970/acbf/acbfdocument.py), [probe method and durable results summary](notes/Portable%20comic%20panel%20metadata/acbf-readers.md#what-was-actually-validated-in-a-scratch-environment))

Negative controls expose two practical traps. Replacing valid points with `not-points` still passed the XSD because `points` is a string; adding `reading-direction` failed 1.1 validation. Schema validity cannot establish coordinate syntax, polygon validity, image bounds, reference resolution, or sensible reading order. The probe did not execute Android archive discovery, image rendering, gestures, or viewport behavior; those code paths were inspected only. Desktop Viewer and Peruse were not launched. Rotation, EXIF orientation, tall panels, overlapping/inset panels, spreads, RTL navigation, and cover-only books remain untested. ([Schema frame definition](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/blob/e033e004e2897fe20ad09cbd649a8ba1d6b38d09/XML%20Schema/acbf-1.1.xsd#L512-L518), [recorded probe evidence](notes/Portable%20comic%20panel%20metadata/acbf-readers.md#what-was-actually-validated-in-a-scratch-environment))

## The local PDF requires whole-page preservation and explicit sequence

The Downloads sample, [Parallel Truths Graphic Novel Anthology – Reader Nation.pdf](</Users/csells/Downloads/Parallel Truths Graphic Novel Anthology - Reader Nation.pdf>), is an unencrypted **257-page, 119 MB PDF**. Read-only inspection found CMYK JPEG2000 imagery, masks, and composed pages. In particular, its contents page renders substantial text/design despite listing only a small embedded raster object. Four rendered pages showed a cover, contents/credits, and comic layouts with inset or overlapping panels. No panel guidance was identified in the inspected XMP metadata; the PDF's complete object graph was not exhaustively searched. ([Local inspection record](notes/Portable%20comic%20panel%20metadata/local-inputs.md#what-does-the-downloads-pdf-imply-for-import))

This means **extracting embedded PDF images is not a general page-import strategy**. A broad importer needs to preserve the visible page composition; image extraction is only an optimization where equivalence is established. Rendering and image extraction expose different things, and color conversion, masks, orientation, clipping, annotations, and output dimensions affect both fidelity and coordinate meaning. Rendering resolution, image encoding, and engine choice remain design decisions. Nothing in this research authorizes dropping regions outside detected panels or altering the source PDF. ([Poppler image-extraction manual](https://skia.googlesource.com/third_party/poppler/+/master/utils/pdfimages.1), [MuPDF page-rendering API](https://mupdf.readthedocs.io/en/1.28.0/reference/javascript/types/PDFPage.html))

The current Flutter application selects one image, sends it to Gemini, and overlays rectangles. Its [service](../../lib/ai_service.dart) requests normalized `ymin, xmin, ymax, xmax` coordinates but does not request reading order; its [model](../../lib/segmentation_models.dart) stores only those four coordinates per panel. Whole-book import, page identity, archive export, and an explicit sequence contract are new work. Inset and overlapping layouts make geometric sorting an assumption to validate, not an established solution. No Gemini call or segmentation-quality assessment was performed on the sample, and the existing provider does not settle the Rust CLI's provider policy.

For terminology, CBZ is ZIP and CBR is RAR. CBC is a distinct collection wrapper: a ZIP containing comic archives plus `comics.txt`. The vision reasonably normalizes the spoken CVR/CVZ variants to CBR/CBZ, while actual CBC support remains an unanswered scope question. Source ordering, nested directories, existing metadata, and duplicate names also need explicit behavior. Conversion should create a separate artifact and preserve originals. ([Archive terminology](https://www.cdisplayex.com/mobile/settings/), [Calibre CBC definition](https://manual.calibre-ebook.com/conversion.html#comic-book-collections))

## Compatibility requirements should lead the next discussion

**Recommendation:** carry ACBF 1.1 inside a conventional CBZ as the leading output candidate, retaining complete pages and encoding panel sequence deliberately. Linux ACBF Viewer/Peruse and Android ACBF Viewer are source-supported consumers to qualify. In the follow-up interview, the user selected **Android as the first-version reading target**, making ACBF Viewer for Android the leading candidate to validate. The metadata format and reader recommendation remain research conclusions; the platform choice does not establish a tested reading experience or require the CLI itself to run on Android.

The decisive boundary is whether success requires a native reader, OSS licensing, direct opening of one CBZ, and particular Apple platforms simultaneously. A hosted browser workflow, a KOReader sidecar, or contributing an importer to another reader changes the product scope; none should silently become part of a conversion CLI. The next discussion should resolve those requirements before choosing implementation details. Subsequent compatibility claims need to name the reader, version, platform, and observed panel sequence on representative books. This report establishes a viable metadata mechanism and specific candidate consumers; it does not establish universal coverage, model accuracy, performance, or an implementation plan.
