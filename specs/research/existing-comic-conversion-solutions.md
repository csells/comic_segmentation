Research checked **2026-10-07**. This report revisits reuse opportunities before implementation; the [vision](../vision/comic-panel-cli.md) remains macOS-first Rust, Gemini with the user's API key, automatic conversion without a correction interface, and Android reading first.

**Pannello is the strongest existing pipeline to evaluate before building whole-book conversion infrastructure.** It already accepts comic archives, PDFs, and image folders, detects ordered panels, and can produce a CBZ retaining complete page images. Four synthetic runs succeeded on this Mac. Its panel output is a KOReader JSON sidecar, however, and the inspected package has neither embedded ACBF export nor a Gemini backend. ACBF Editor already connects automatic detection to ACBF-in-CBZ export, but through a graphical, page-by-page workflow. No exact complete match for the accepted requirements was verified; that is a scoped search result, not proof none exists. The immediate reuse question is whether extending a Python pipeline is acceptable, or whether Rust remains firm enough to favor narrower component reuse. ([Pannello source](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/core.py), [CLI](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/cli.py), [ACBF Editor detector](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/frames_editor.py#L1295-L1316))

## Pannello comes closest to the automatic workflow

The target artifact remains complete pages plus ordered regions embedded in one CBZ. ACBF 1.1 provides image-pixel polygons in frame-element order; Android ACBF Viewer has a verified parser and inspected frame-navigation code, although its GUI has not been tested here. Custom JSON, cropped-panel pages, and Kindle magnification markup do not provide that same compatibility contract. ## Synthetic execution proves plumbing and exposes preservation gaps

Pannello ran in a fresh virtual environment on macOS 26.6.2 arm64 with Python 3.13.12 and OpenCV 4.14.0.94. Each fixture contained a blank cover, a four-panel grid, and a two-panel grid. All four commands exited successfully and produced panel counts **1, 4, 2**; the cover received a whole-page rectangle and a fallback notice. ([Recorded results](notes/Existing%20comic%20conversion%20solutions/pannello-smoke-report.json), [reproduction script](notes/Existing%20comic%20conversion%20solutions/pannello-smoke.py), [dependency versions](notes/Existing%20comic%20conversion%20solutions/pannello-smoke-requirements.txt))

| Run | Observed output | Consequential result |
| --- | --- | --- |
| CBZ, direct | JSON only | Read RTL from ComicInfo; naturally sorted `page1`, `page2`, `page10`. |
| CBZ, repack | Three PNGs in CBZ plus JSON | Image bytes preserved; ComicInfo and auxiliary notes omitted; direction changed to LTR. |
| PDF, repack | Three rendered JPEGs in CBZ plus JSON | All synthetic pages retained, including the blank cover. |
| Folder, repack | Three PNGs in CBZ plus JSON | Image bytes preserved. |

The source CBZ and folder-image hashes remained unchanged, and **none of these outputs contained ACBF**. Repacking before detection drops the XML from which direction was inferred, explaining the RTL regression. Source inspection also found write-mode output creation without general collision refusal: rerunning can replace generated output. Those behaviors conflict with this project's preservation requirements, even though these isolated tests left their sources untouched. ([Smoke results](notes/Existing%20comic%20conversion%20solutions/pannello-smoke-report.json), [repack and output code](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/core.py), [CLI ordering](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/cli.py))

A separate unmodified Kumiko test adds a crucial quality limit. OpenCV 5.0.0.93 failed with an `IndexError`; pinning 4.14.0.94 allowed simple LTR/RTL grids to work. A framed inset inside a larger panel yielded only the outer rectangle. **Successful detection can therefore be wrong without triggering error fallback.** This does not establish that Gemini performs better; no comparison was run. No user comic was processed by these converters or detectors, no API request or pretrained-model download occurred, and no Android UI was exercised. CBR and other archive edge cases remain source-inspected. ([Kumiko implementation](https://github.com/njean42/kumiko/blob/9d587ae9498bc84dfda06fc19c6ad89f421bec14/lib/page.py), [runtime evidence](notes/Existing%20comic%20conversion%20solutions/detection-components.md#what-are-the-deployment-licensing-and-quality-limits))

## Existing interfaces provide useful integration points

Pannello already separates extraction, page listing, repacking, generation, and normalization into callable functions. Its CLI offers `--repack-only`; PDF import uses Poppler page rendering, preserving composition rather than treating embedded image objects as complete pages. RAR depends on `unrar`, and its base Python/OpenCV stack needs no model download. This supplies substantial reusable infrastructure, but also retains Python and external-tool deployment. ([Core interfaces and importers](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/core.py), [CLI](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/cli.py))

The clearest ACBF adapter boundary is Pannello's ordered, normalized `x,y,w,h` result. An adapter must obtain actual page dimensions, convert rectangles to integer pixel polygons, preserve their sequence and page association, handle cover/body separation, and embed one root ACBF file beside complete page images. Pannello's JSON omits dimensions and rounds coordinates to four decimals; these details matter when choosing whether to consume JSON or integrate earlier. Its internal `detect_pages_model(..., engine=...)` accepts an engine object, but the inspected CLI has no general provider contract and no Gemini implementation. **A Gemini extension is new work**, not an existing switch. ([Output and engine interfaces](https://github.com/marcopiraccini/pannello/blob/d4747266b5e8ac478168050f75c9ea71bba00e85/pannello/core.py), [ACBF embedding specification](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF/wiki/Specifications#embedding-acbf-files-and-compatibility-with-popular-comic-book-formats))

Metadata libraries warrant evaluation before writing serialization. Python **libacbf** models ordered frames, separates cover/body, validates before saving, and supports exclusive new-file creation. It is BSD-3-Clause, but was archived in 2023; its latest inspected code is from 2021 and current interpreter compatibility was not tested. Peruse's distinct C++/Qt `acbf` library exposes document/frame writers under LGPL terms, but its current writer hardcodes the **1.2 namespace**, unsuitable unchanged for the conservative 1.1 profile. Krita's exporter and ACBF Editor's rectangle-to-frame code are concrete references with GUI dependencies and GPL licensing. ([libacbf status/license](https://github.com/Grafcube/libacbf), [tutorial](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/docs/source/tutorial.rst), [Peruse writer](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/AcbfDocument.cpp#L64-L82), [Krita exporter](https://github.com/KDE/krita/blob/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c/plugins/python/comics_project_management_tools/exporters/CPMT_ACBF_XML_Exporter.py))

A scratch serializer test would establish whether maintaining a pinned Python helper is preferable to a narrow Rust adapter built on established XML tooling. No libacbf execution or generic ACBF adapter was completed during this research. Reusing a format is also distinct from copying its implementation: source-code terms remain attached to borrowed code.

## Detector reuse involves separate code, weight, and runtime choices

The existing [Gemini service](../../lib/ai_service.dart) supplies a useful normalized-box starting point, and Google's API documents structured image detection. It still needs explicit reading-order semantics for this product. Existing local detectors are useful comparison baselines; their discovery does not change the approved Gemini provider. ([Google image-understanding documentation](https://ai.google.dev/gemini-api/docs/image-understanding#object-detection))

OpenComic AI returns masks and rectangles; `.panels.path()` means SVG contours, not reading order. Its returned `probability` is hardcoded to one, so it cannot decide when detection needs rescue. Reading order lives separately in the reader. Magi likewise uses geometric ordering heuristics. These components prevent a need to invent another detector, but none establishes dependable narrative order on the user's comic or justifies an automatic multi-engine cascade. Model-card and downstream NOTICE claims should not override conflicting upstream terms. ([OpenComic inference](https://github.com/ollm/opencomic-ai-bin/blob/f4d2a82fcd08b31c0796cbe4161da6c1765f0114/src/panels.mts), [reader ordering](https://github.com/ollm/OpenComic/blob/165826057755d71d1dcf466836c518ef87cc2c6f/scripts/reading/panels.mts#L221), [Magi ordering](https://huggingface.co/ragavsachdeva/magi/blob/15ad498ad45093ad3b833d625728220c6309ad99/utils.py#L174))

## The consequential choice is how firmly Rust constrains reuse

**Recommendation:** evaluate extending Pannello as the strongest existing near-match before committing to a new whole-book pipeline. A Python extension retains the most existing machinery. A Rust subprocess wrapper retains that machinery plus its Python/runtime dependencies. Keeping Rust and Gemini while selectively reusing import tools, schemas, fixtures, and small adapters preserves the accepted direction but shares less application code. These are different ownership and distribution choices; the evidence does not support an effort estimate or silently choosing one.

Every route still needs preservation-safe output, correct page/metadata ordering, Gemini retry and failure reporting, ACBF validation, and an actual Android reading test. Detection failure after retries must produce a complete page without guidance and report it clearly; a detector's plausible but incorrect result remains a separate accuracy problem. Evaluating representative pages during development does not introduce a user-facing review/correction step. No implementation plan or application changes have been made. The next decision is whether Rust is a firm product constraint or a preference that can yield to substantial Python reuse; Gemini remains accepted unless explicitly reconsidered.
