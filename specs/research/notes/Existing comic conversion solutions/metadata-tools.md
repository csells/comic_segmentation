# Existing ACBF authoring, export, and reader detection tools

## Which existing applications already create panel metadata inside CBZ?

### Takeaway

ACBF Editor already joins automatic raster panel detection to ACBF-in-CBZ export, but through a graphical editor rather than a documented unattended whole-book detection command. Peruse Creator and Krita's Comics Project Management Tools provide genuine ACBF exporters driven by authored geometry; neither inspected workflow automatically segments arbitrary imported raster comics. These are partial reuse candidates, not verified replacements for the proposed macOS CLI. [Editor detector](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/frames_editor.py#L1295-L1316), [Peruse editor](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/creator/qml/BookPage.qml), [Krita exporter](https://github.com/KDE/krita/blob/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c/plugins/python/comics_project_management_tools/README.md#ACBF).

### Cited Findings

- **ACBF Editor**, inspected at `b1941df35ab79b155eebf8b1d9c56171049c2d3e` (2025-01-27): README labels the GTK4 implementation WIP and requires GTK 4.10+, Python dependencies and a separate Kumiko checkout. Package metadata says `3.0.0a`, while `constants.VERSION` says `1.18`; cite the commit instead of presenting those as a coherent release. [README](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/README.md), [package metadata](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/pyproject.toml), [version constant](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/constants.py#L29), [commit](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/commit/b1941df35ab79b155eebf8b1d9c56171049c2d3e).
- Its `FramesEditorDialog.find_frames()` calls `Kumiko.parse_image()` for the selected page, reads `get_infos()[0]["panels"]`, converts `[x,y,width,height]` to four polygon points and inserts them into the frame model. The invocation hardcodes `rtl:false`. F8/F triggers it; saving emits frame elements in model order. This is actual automatic detection integration, but page selection/trigger/save remain GUI workflow. [Detection and trigger](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/frames_editor.py#L1295-L1316), [serialization](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/frames_editor.py#L1505-L1523).
- `MainWindow.write_file()` writes ACBF 1.1 XML and ZIPs complete extracted files into CBZ. `FilePrepare` imports ZIP/CBR and converts ACV `comic.xml` frames with normalized `relativeArea="x y width height"` to pixel polygons, retaining their traversal order. It also imports ComicInfo catalog fields; that does not turn ComicInfo itself into a panel schema. [Writer](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/main.py#L1214-L1265), [ACV conversion](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/fileprepare.py#L139-L180).
- The CLI supports input/output, image format, quality, resizing and text-layer output, but the inspected option parser has no batch detection option. It imports GTK before parsing and creates a `Gtk.Application`/main window. Thus “has CLI conversion” is not evidence of a portable headless detector. Source files are GPL-3.0. [Entrypoint and license header](https://github.com/ACBF-Advanced-Comic-Book-Format/ACBF-Editor/blob/b1941df35ab79b155eebf8b1d9c56171049c2d3e/src/acbfe.py).
- **Peruse Creator**, inspected at `476daab38422a91e2196920329541f3dc7967c30` (2026-09-25), exposes manual page/frame editing. Its CLI accepts a file positional argument and launches QApplication/QML; no conversion/detection command was found there. `ArchiveBookModel::saveBook()` uses KZip to save `metadata.acbf` and copies original archive entries. The official Creator page still labels the application unreleased; that differs from the separately released Peruse reader. [CLI](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/creator/main.cpp#L58-L78), [archive writer](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/qtquick/ArchiveBookModel.cpp#L512-L568), [Creator listing](https://apps.kde.org/perusecreator/), [commit](https://github.com/KDE/peruse/commit/476daab38422a91e2196920329541f3dc7967c30).
- **Krita CPMT**, inspected at the plugin's latest modifying commit `7588b7e5989d992fa9b4f5ab517fd3dbed178a3c` (2026-09-28), finds shapes in named `panels`/`text` vector layers and derives frame order from shape stacking. The exporter transforms geometry for the output page and writes ACBF 1.1 into CBZ plus a standalone ACBF document. `CPMT_ACBF_XML_Exporter.write_xml(configDictionary,pageData,pagesLocationList,...)` is the concrete seam; it depends on PyQt and a translation parser. Its file license is GPL-3.0-or-later. It exports preauthored vectors rather than discovering panels in a raster PDF. [Authoring contract](https://github.com/KDE/krita/blob/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c/plugins/python/comics_project_management_tools/README.md#ACBF), [shape extraction](https://github.com/KDE/krita/blob/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c/plugins/python/comics_project_management_tools/comics_exporter.py#L370-L430), [exporter and license](https://github.com/KDE/krita/blob/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c/plugins/python/comics_project_management_tools/exporters/CPMT_ACBF_XML_Exporter.py), [commit](https://github.com/KDE/krita/commit/7588b7e5989d992fa9b4f5ab517fd3dbed178a3c).

### Inferences

- Extending ACBF Editor with a non-GUI batch path is a credible project if Python/GTK lineage is acceptable; it would reuse a detector-to-metadata integration rather than inventing one. A Rust wrapper around its current CLI would still lack unattended detection and retain GUI dependencies.
- Krita is useful when source comic projects already contain vector frames. Importing arbitrary PDFs into an authoring project merely to reach its exporter adds work unrelated to the desired CLI.

### Gaps

- No application was installed or launched. This was source inspection on macOS, not proof that an editor's detector/save combination works correctly across a book.
- No PDF renderer, failure-resumption policy, safe immutable output workflow, or Gemini adapter was established in these inspected authoring paths. The full applications may support additional workflows elsewhere.

## Which reusable libraries and serialization seams avoid reimplementing metadata?

### Takeaway

The most direct headless ACBF library found is Python **libacbf** under BSD-3-Clause, but it is archived and needs a maintenance evaluation. Peruse supplies a separately built C++/Qt library with a stronger application integration story, at the cost of Qt/FFI dependencies and an important current ACBF-version mismatch. [libacbf](https://github.com/Grafcube/libacbf), [Peruse library build](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/CMakeLists.txt).

### Cited Findings

- **libacbf** latest inspected commit is `021fad7d8d59d1abd40f0fe926d04f545fa50210` (2021-11-09); GitHub says archived May 25, 2023. PyPI's latest version is 1.0.2, released August 24, 2021. Its repository license is BSD-3-Clause. [Archive status](https://github.com/Grafcube/libacbf), [commit](https://github.com/Grafcube/libacbf/commit/021fad7d8d59d1abd40f0fe926d04f545fa50210), [PyPI release](https://pypi.org/project/libacbf/1.0.2/), [license](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/LICENSE).
- `ACBFBook(path,'x')` creates a new ZIP-backed book and rejects an existing path; `archive_type=None` creates plain XML. The library handles ZIP/7z/TAR and read-only RAR. It models `Page.frames` as ordered `Frame` objects, emits point lists, serializes cover/body separately and validates against bundled ACBF XSDs before saving. It does not detect panels. [Tutorial](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/docs/source/tutorial.rst), [frame model](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/libacbf/body.py#L418), [writer](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/libacbf/libacbf.py#L610-L670), [save validation](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/libacbf/libacbf.py#L759-L782).
- A thin helper could accept the CLI's page manifest and ordered rectangles, populate cover/body/frames and call `get_acbf_xml()`; archive creation can remain outside the helper. That is an integration inference grounded in public methods, not an existing supplied conversion CLI. Source imports `magic`, `py7zr`, `rarfile`, `dateutil`, `langcodes` and `distutils.util`; compatibility with today's interpreter/dependency releases was not established. [Methods/imports](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/libacbf/libacbf.py), [dependencies](https://github.com/Grafcube/libacbf/blob/021fad7d8d59d1abd40f0fe926d04f545fa50210/requirements.txt).
- **Peruse libacbf** is a distinct C++ library, not Grafcube's Python project. CMake builds shared `acbf` linked to Qt6 Core and installs headers/export configuration. `Document::toXml()`, `Page::addFrame()` and `Frame::toXml()` provide the needed model/writer path; file headers use LGPL-2.1-or-later with KDE's version-acceptance language. However, current `Document::toXml()` hardcodes the **ACBF 1.2 namespace**, so it cannot simply be adopted unchanged for the conservative 1.1 profile. [CMake](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/CMakeLists.txt), [namespace and license](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/AcbfDocument.cpp#L64-L82), [frame writer](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/AcbfFrame.cpp#L55-L72), [page insertion](https://github.com/KDE/peruse/blob/476daab38422a91e2196920329541f3dc7967c30/src/acbf/AcbfPage.cpp#L360-L385).

### Inferences

- **Wrap/evaluate first:** a scratch-only libacbf serializer smoke test is the smallest useful next reuse experiment. If it works, compare maintaining a pinned Python helper against a narrow Rust writer built on an established XML crate. Do not label an archived library production-ready based only on its old PyPI classifier.
- **Reference/adapt selectively:** ACBF Editor provides useful ACV-to-ACBF conversion and frame-to-XML examples. Peruse provides library interfaces and archive-copy behavior. Direct copying/translation carries the respective code license; interoperability with the XML format and reuse of code are separate decisions. These are observed license boundaries, not a complete distribution compliance assessment.
- **Avoid broad rewrites:** a supported XML crate plus the established ACBF schema may be a smaller owned adapter than shipping Qt or adopting an archived Python archive layer. That choice still needs the proposed smoke test and dependency review; finding no Rust-specific ACBF library here is not proof that none exists.

### Gaps

- No libacbf execution: this environment has lxml/Pillow but lacks `magic`, `py7zr`, `rarfile`, `dateutil`, and `langcodes`; dependencies were not installed just for the experiment. GTK and PyQt were also absent. No synthetic exporter result is claimed.
- No macOS packaging, security audit, concurrency behavior or lossless preservation of arbitrary preexisting ACBF was tested. Treat importer/writer code as reuse candidates requiring validation, not ready-made trustworthy handling of user archives.

## Can Chika replace the converter or consume its prepared panels?

### Takeaway

Chika offers a credible alternative product experience: Android reads CBZ/CBR and detects panels locally. The inspected source does **not** establish ACBF/ACV prepared-panel import or export, so adopting it as-is does not fulfill the portable metadata CBZ objective. [README](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/README.md), [archive interface](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/shared/src/commonMain/kotlin/com/chakra/comicreader/data/archive/ComicArchive.kt), [panel source](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/app/src/main/java/com/chakra/comicreader/detection/PanelSource.kt).

### Cited Findings

- Inspected commit `d014fde9f6e739977b957665d9ae71ff422597d2` is dated 2026-09-06. The repository supplies Android and iOS/shared source; this investigation focused on Android. Its source is MPL-2.0. The README describes TFLite YOLO detection and CBZ/CBR/RAR5 support. [Commit](https://github.com/batunii/chika/commit/d014fde9f6e739977b957665d9ae71ff422597d2), [README/license boundaries](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/README.md#license).
- Android `ZipComicArchive` filters entries to images and naturally sorts filenames. `ReaderViewModel.panelsFor()` calls `panelSource.detect(bitmap,rightToLeft)` then caches the results in a `HashMap`; the Room entity persists book information and reading position, not panel coordinates. Repository searches for `acbf`, ACV, panel JSON and archive export found no prepared-panel import/export path in inspected Android/shared sources. This negative finding is scoped to those source paths. [ZIP loader](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/app/src/main/java/com/chakra/comicreader/data/archive/ZipComicArchive.kt), [reader cache](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/app/src/main/java/com/chakra/comicreader/ui/reader/ReaderViewModel.kt#L173-L188), [database entity](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/app/src/main/java/com/chakra/comicreader/data/db/ComicEntity.kt).
- Useful algorithm seams already exist in pure Kotlin: `PanelOrdering` implements recursive X/Y cuts with tolerance, while `PanelPipeline.zoomRegions()` calls gap filling, ordering, merge/divide planning and padding. These produce reading viewports, which can merge small panels or split large ones; they are not necessarily one region per original artistic panel. Current pipeline fallback can split a full-page region through its planner, despite the README's simpler “whole page” description. [Ordering](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/shared/src/commonMain/kotlin/com/chakra/comicreader/detection/PanelOrdering.kt), [pipeline](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/shared/src/commonMain/kotlin/com/chakra/comicreader/detection/PanelPipeline.kt).
- The project distinguishes MPL code from its model, dependencies and excluded brand assets. Its own notices flag unresolved ambiguity around Manga109-s-trained model redistribution despite the upstream weights' Apache-2.0 label; do not represent the entire detector stack as unconditionally permissive. This is an upstream disclosed uncertainty, not an independently resolved legal conclusion. [Third-party notices](https://github.com/batunii/chika/blob/d014fde9f6e739977b957665d9ae71ff422597d2/THIRD_PARTY_NOTICES.md#bundled-model--training-data).

### Inferences

- **Adopt as a reader alternative** only if the desired outcome changes to local reader-side detection. It avoids the converter but leaves portable prepared metadata unresolved.
- **Extend as a reader** by adding ACBF extraction to the archive layer and a prepared-panel source before `MlPanelDetector`; this is a concrete seam but creates an additional maintained application project. It should not become an implicit v1 requirement.
- **Overall recommendation:** reuse a proven whole-book detector/conversion pipeline where separately verified, add only an ACBF adapter, and evaluate libacbf before choosing its implementation. Keep ACBF Editor's conversion code and Peruse/Krita serializers as references and interoperability fixtures. None of these five inspected candidates was demonstrated to satisfy unattended PDF/CBR/CBZ/folder → preserved-pages CBZ + ACBF on macOS without extension.

### Gaps

- No Android/iOS build or device test was performed. Detection quality, fallback behavior in a running reader, and model licensing conclusions remain unverified.
- Research performed 2026-10-07 using public project documentation and pinned source archives in scratch space. No user PDF was uploaded or modified; no API inference, GUI installation or application-source changes occurred. Pannello and standalone detector comparisons are covered by the other research notes, not duplicated here.
